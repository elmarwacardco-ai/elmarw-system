# بوت واتساب المروة — المواصفات المعتمدة وخطة التنفيذ

> **الحالة:** هذه وثيقة تنفيذ متفق عليها وليست ادعاءً بأن بوت واتساب متصل أو يعمل بالفعل.
> زر واتساب اليدوي في كارت الأوردر تم إضافته على فرع التطوير؛ الربط الآلي مع واتساب وإنشاء المسودات لم يُفعّلا بعد.
> لا تعدّل أو تحذف الوظائف الأصلية للموقع مقابل إضافة البوت.

## 1. رحلة الطلب المعتمدة

1. بوت واتساب يعرض نفس **العملاء والأقسام والمنتجات والكميات وأسعار B وVIP** المستعملة في نظام المروة الحالي، حسب حساب العميل.
2. العميل يختار المنتج والكمية ويكتب **اسم الشغل** ويرفق **PDF إلزاميًا**.
3. طلب واتساب يدخل النظام كـ **مسودة مراجعة** فقط. **لا** يُنشأ أوردر رسمي ولا سيريال عند الاستلام.
4. أول موظف يضغط «بدء المراجعة» يحجز تعديل المسودة. ينتهي الحجز بعد **15 دقيقة من عدم النشاط**؛ القراءة لباقي الموظفين مسموحة، والتعديل لصاحب الحجز فقط.
5. الموظف يراجع تفاصيل الطلب وملف PDF. لو فيه مشكلة، يضغط زر **واتساب العميل** ليفتح المحادثة ويتواصل بنفسه؛ **ممنوع** إرسال طلب تلقائي من البوت لرفع PDF بديل.
6. بعد التواصل، **الموظف نفسه** يرفع PDF المصحح من شاشة مراجعة المسودة. تُحفظ كل نسخ PDF القديمة مع تاريخ ومن رفعها؛ وتُميّز نسخة التنفيذ المعتمدة، دون حذف القديمة.
7. الموظف يُحدد **موعد التسليم** ثم يضغط «اعتماد الطلب». عند الاعتماد فقط تنشأ بيانات الأوردر الرسمي ويصدر السيريال بصيغة النظام المعتمدة؛ لا ينشأ سيريال لمسودة قبل الاعتماد.
8. الموظف يرسل تأكيد الأوردر إلى العميل **يدويًا**. إذا تأخر إرسال التأكيد **10 دقائق** بعد الاعتماد يظهر تنبيه للموظفين؛ لا يرسل النظام رسالة تأكيد نيابة عن الموظف.

## 2. شروط الصحة والصلاحيات

- يجب توثيق مصدر الرسائل الواردة والتحقق من توقيع **Meta WhatsApp webhook** قبل قبول أي طلب، ومنع تكرار الرسائل باستخدام معرف رسالة فريد.
- لا يرسل النظام رسائل إلى العملاء تلقائيًا بشأن مشاكل PDF أو تأكيد الطلب.
- اربط عميل واتساب بحساب مسموح بعد تحقق ملكية الهاتف؛ لا تعتمد على رقم الهاتف المرسل وحده لإعطاء أسعار VIP أو بيانات أوردرات خاصة.
- استخدم Supabase Storage **خاصًا** مع سياسات تنزيل محدودة المدة لكل PDF. لا تعرض روابط ملفات تنفيذ عامة.
- اجعل «اعتماد المسودة» عملية ذرّية تتحقق من حجز الموظف وصلاحية موعد التسليم، وتُنشئ **أوردرًا واحدًا فقط** لكل مسودة لتجنب التكرار عند إعادة طلب الشبكة.
- الحجز الزمني: الحقول المقترحة `locked_by`, `locked_at`, `last_activity_at`. التحقق من انقضاء الحجز يكون في السيرفر، وليس في واجهة React فقط.
- نسخ المرفقات: `version`, `uploaded_by`, `uploaded_at`, `storage_path`, `is_approved`. لا تسمح بالاستبدال أو الحذف الصامت لنسخة قديمة.
- متابعة تأكيد الموظف: `approved_at`, `confirmation_sent_at`, `confirmation_sent_by`. يظهر تنبيه في الداشبورد عند تجاوز 10 دقائق مع غياب إرسال التأكيد.
- حافظ على سريان كل أجزاء السيستم الأصلي: العملاء، المنتجات، السعر B/VIP، السيريال، الأوردرات، الفولدرات، المدفوعات، الطباعة والداشبورد.

## 3. تقسيم التنفيذ

1. **المرحلة A — مكتمل على فرع التطوير فقط:** زر واتساب يدوي في كارت كل أوردر صالح ورقم هاتف مصري صحيح، مع اختبارات التطبيع؛ بدون رسائل آلية.
2. **المرحلة B — لم يبدأ تشغيلها:** جدول مسودات مراجعة خاص ومستودع نسخ مرفقات + API إدارية لإنشاء/عرض/حجز/تعديل/اعتماد المسودات مع اختبارات التزامن وصلاحيات المستخدمين.
3. **المرحلة C — لم تبدأ:** شاشة React لإدارة مسودات واتساب، رفع نسخ PDF، موعد التسليم، الموافقات، والتنبيه بعد 10 دقائق.
4. **المرحلة D — لم تبدأ:** ربط Meta WhatsApp Business Cloud API/Webhook والتحقق من المصدر، تفعيل التكامل في Preview، ثم اختبار تحويل رسالة حقيقية إلى مسودة ومراجعتها والموافقة عليها.
5. **الإطلاق:** بعد اختبار هوية العملاء وصلاحيات الموظفين، وحماية الملفات، وعلاج مشكلات الأمان المفتوحة في طلب المراجعة #1.

**مهم:** لا توجد أي هجرات قاعدة بيانات أو تكامل رسائل مفعل نتيجة إنشاء هذه الوثيقة. لا يُنشر البوت للجمهور قبل اختبارات Preview واستيفاء صلاحيات Meta ومتطلبات حماية البيانات.
